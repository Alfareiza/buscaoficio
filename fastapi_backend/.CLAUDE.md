# Backend (fastapi_backend)

## Stack
- FastAPI (async) on Uvicorn/Starlette, Python 3.12, deps managed via **uv** (`uv.lock`)
- Pydantic v2 + pydantic-settings for schemas/config
- Auth: **fastapi-users** (JWT + user CRUD primitives) fronting a custom passwordless email-OTP flow — see "Auth architecture" below
- SQLAlchemy 2 (async) + asyncpg, PostgreSQL 17, Alembic (async) for migrations
- fastapi-pagination for list endpoints
- fastapi-mail for outgoing email; local dev catches mail in MailHog (`:8025`)
- FastAdmin mounted at `/admin` for a quick DB admin UI
- sentry-sdk[fastapi] for errors + tracing + logs
- Tests: pytest / pytest-asyncio, coverage reported to Coveralls
- Quality: Ruff (lint/format) + mypy, run via pre-commit

## Auth architecture (read before touching login/register/token code)
Full write-up: `docs/auth.md`. Deeper narrative/history: `memory-bank/systemPatterns.md` § "Auth pattern" / "Passwordless OTP auth pattern" / "JWT refresh token rotation".

- **Login and registration are one passwordless email-OTP flow**, not password auth. Password-based `/jwt/login`, `/register`, `/register/cliente`, `/register/profesional` were removed 2026-08-18. `/forgot-password`, `/reset-password`, `/request-verify-token`, `/verify` still exist but are vestigial.
- Flow: `POST /otp/request` (email → 6-digit code, always 202, anti-enumeration) → `POST /otp/verify` (email+code → logs in an existing user, or returns a short-lived signed `registration_token` for a new email) → `POST /register/cliente/otp` or `/register/profesional/otp` (registration_token + profile fields → creates the account and logs in).
- **No account row is created until registration completes** — an abandoned signup never leaves a ghost user. OTP-created accounts get a random, never-disclosed password (fastapi-users requires a non-null `hashed_password`) and `is_verified=true` immediately (entering the code already proves mailbox ownership).
- Codes live in `email_otps`, SHA-256 hashed, 10 min expiry (`OTP_CODE_EXPIRE_SECONDS`), max 5 verify attempts, 60s resend cooldown, keyed by `email` (not `user_id`, since the account may not exist yet). Rows are never purged (known gap).
- **Session issuance is shared**: `build_session_response()` is called by OTP verify and both OTP registration routes — the same function password login used to call.
- Two permission levels only: `current_active_user`, `current_superuser` (FastAPI `Depends`); no RBAC beyond the `is_superuser` flag.
- Passwords hashed with Argon2 (primary) + bcrypt (fallback) via pwdlib / fastapi-users `PasswordHelper`. To verify: `PasswordHelper().verify_and_update(plain, stored_hash)` — never re-hash and compare.
- No `createsuperuser` CLI yet — create a user via OTP sign-up or FastAdmin, then promote via SQL.
- fastapi-users has no `get_by_id`; fetch a user inside a custom route with `user_manager.get(user_id)`.

### JWT refresh token rotation
- Access token: JWT, 15 min (`ACCESS_TOKEN_EXPIRE_SECONDS`), returned in the response body, sent as `Authorization: Bearer`.
- Refresh token: opaque random string, 30 days (`REFRESH_TOKEN_EXPIRE_SECONDS`), HttpOnly/Secure/SameSite=Strict cookie, path-scoped to `/api/v1/auth/jwt/refresh` only.
- Paired **fingerprint cookie** (double-submit pattern): both raw values must be presented together on refresh; both are SHA-256-hashed and compared against the stored `RefreshToken` row. A leaked refresh token alone is useless without the paired HttpOnly cookie.
- Every successful refresh **rotates**: revokes the old row, inserts a new one. Replaying an already-rotated (revoked) token is treated as theft — `detect_theft_and_revoke` revokes **every** active refresh token for that user and the request gets 401.
- `POST /auth/jwt/logout` revokes all refresh tokens for the user (every device/session, not just current).
- No cleanup job yet for expired/revoked rows in `refresh_tokens` or `email_otps`.

## Database migrations
- Never run `make docker-migrate-db` / `alembic upgrade head` without the user explicitly reviewing the migration file first. Generating a migration (`make docker-db-schema`) and applying it (`make docker-migrate-db`) are separate steps on purpose, always stop after generating and let the user (or an explicit follow-up instruction) approve before applying.
- `alembic revision --autogenerate` cannot detect renames. A `__tablename__` or column rename in `models.py` will autogenerate as a destructive `drop_table`/`create_table` (or `drop_column`/`add_column`) pair, silently deleting existing rows on apply. Before presenting any autogenerated migration, inspect it for drop+create pairs that represent the same renamed entity and rewrite them as `op.rename_table(...)` / `op.alter_column(..., new_column_name=...)`. Check for existing data (`SELECT count(*) FROM <table>;`) before treating any rename as safe, even in a dev database.
- See `fastapi_backend/README.md` → "Database & Alembic" → "⚠️ Migration safety" for the full rationale (a real near-loss of the project's superuser row).
- Changing `models.py` alone does **not** update the OpenAPI schema (watcher doesn't watch it) and does **not** migrate the DB. After a model change: update schemas/routes if the API should change, then `make docker-db-schema migration_name="…"` → review → `make docker-migrate-db`.
- Alembic uses `DATABASE_URL` (not `TEST_DATABASE_URL`). Inside Compose, connect to `db:5432`/`db_test:5432`; from the host use the mapped ports (see "Local ports" below).

## Logging & Sentry
- Single logger: `from app.config import logger` (`logging.getLogger("buscaoficio")`). Use **f-strings** in log messages, not `%s`.
- `LoggingIntegration` forwards INFO+ to Sentry logs/breadcrumbs, ERROR+ to issues. `send_default_pii=False`. Never log tokens, passwords, or JWTs.
- Sentry sample rate 1.0 unless `SENTRY_ENVIRONMENT=production` (then 0.1). Empty `SENTRY_DSN` disables Sentry entirely; also skipped whenever `"pytest" in sys.modules`.

## FastAdmin
- Reads `ADMIN_*` from `os.environ` at import time — `load_dotenv()` runs in `app/__init__.py` so `.env` is loaded before `from fastadmin import fastapi_app`.
- `ADMIN_SITE_HEADER_LOGO` / `ADMIN_SITE_SIGN_IN_LOGO` are **public URL paths** (e.g. `/static/images/logo/busca-oficio-logo-principal.svg`), not filesystem paths. Files must live under `app/static/`, served at `/static`. A Next.js `public/` path will 404 on the API origin.
- Local HTTP dev needs `ADMIN_SESSION_COOKIE_SECURE=false`.

## Testing gotchas
- `tests/conftest.py`'s `test_client` fixture uses `base_url="https://localhost:8001"` (not `http://`) — required so httpx's cookie jar actually sends Secure-flagged cookies (refresh/fingerprint) on later requests in the same test. `http://` silently drops them, producing 401s that look like an auth bug but are actually a test-harness artifact.
- Any DB write inside a route handler needs an explicit `await db.commit()`, not just `flush()` — the test harness's `override_get_async_session` rolls back anything left uncommitted when it closes the session after the request.
- After an HTTP call through `test_client`, don't call `await db_session.refresh(some_earlier_object)` — the fixture closes `db_session` in a `finally` after requests that resolve `get_user_db` (most authenticated routes), so the object leaves the session's identity map and `.refresh()` raises `InvalidRequestError`. Re-query fresh instead: `(await db_session.execute(select(Model).where(...))).scalar_one()`.
- To test OTP-driven flows, mock `app.routes.auth.send_otp_code_email` with an autouse `mocker.patch(...)` fixture, then read the real code back via `mock_send_otp_email.call_args[0][1]` after calling `/otp/request` — see `tests/routes/test_auth_otp.py`. Other tests needing a logged-in session (e.g. `test_auth_refresh.py`) reuse this as their login helper instead of hitting a login route directly.

## Commands
- `make start-backend` (or `make docker-start-backend`) — runs `./start.sh`, which starts FastAPI **and** `watcher.py`. Prefer this over a bare `uv run fastapi …`, which starts the app without the OpenAPI watcher.
- `make test-backend` / `uv run pytest` (or `make docker-test-backend`)
- `make docker-db-schema migration_name="…"` → review → `make docker-migrate-db`
