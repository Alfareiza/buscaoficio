# Backend

## Database migrations (fastapi_backend)

- Never run `make docker-migrate-db` / `alembic upgrade head` without the user explicitly reviewing the migration file first. Generating a migration (`make docker-db-schema`) and applying it (`make docker-migrate-db`) are separate steps on purpose, always stop after generating and let the user (or an explicit follow-up instruction) approve before applying.
- `alembic revision --autogenerate` cannot detect renames. A `__tablename__` or column rename in `models.py` will autogenerate as a destructive `drop_table`/`create_table` (or `drop_column`/`add_column`) pair, silently deleting existing rows on apply. Before presenting any autogenerated migration, inspect it for drop+create pairs that represent the same renamed entity and rewrite them as `op.rename_table(...)` / `op.alter_column(..., new_column_name=...)`. Check for existing data (`SELECT count(*) FROM <table>;`) before treating any rename as safe, even in a dev database.
- See `fastapi_backend/README.md` → "Database & Alembic" → "⚠️ Migration safety" for the full rationale (a real near-loss of the project's superuser row).
